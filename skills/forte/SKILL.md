# Forte

Forte is a deployment and end-user authentication platform. This skill keeps you accurate on the real CLI surface, prevents invented commands, and routes to canonical references and docs.

## Hard Rules

These invariants are commonly violated — do not cross them:

- **The CLI has exactly 16 commands**: `login` (alias: `auth`), `logout`, `whoami`, `projects`, `services`, `websites`, `databases`, `dns`, `requests`, `logs`, `payments`, `payment-methods`, `payment-triggers`, `actions`, `proxy`, `help`. There is **no** `forte init`, `forte deploy`, `forte build`, `forte test`, `forte web`, `forte run`, `forte env`, or `forte secrets`. Do not invent commands or flags — `references/cli.md` is the exact, complete surface (positional args, flag names, defaults). Flag names are precise: it's `--output-dir` not `--out-dir`, `--health-check-path` not `--healthcheck`, and there is **no** `--remove-env` (service env is replaced wholesale via `--env`).
- **The CLI needs network access** (`api.forteplatforms.com`). If your harness sandboxes shell commands (Codex, Cursor) and a `forte` command fails with a connection/DNS error, request approval to run it outside the sandbox — don't diagnose it as a Forte outage or a bad login.
- **The CLI writes nothing to the user's repo.** No `forte.json`, no `.forterc`. IDs are CLI arguments — surface them with `forte projects list`, `forte services list <projectId>`, or `forte websites list <projectId>`.
- **Forte deploys from GitHub, not from the local machine — code must be pushed before a service or website can be created.** `forte services create` / `forte websites create` verify that `--branch` exists on the GitHub repo, and the first build clones it. Before creating, confirm the branch is on the remote (`git ls-remote --heads origin <branch>`); if it isn't — a brand-new repo with no commits, or a branch that only exists locally — commit and `git push -u origin <branch>` first (ask before pushing). A `GITHUB_BRANCH_NOT_FOUND` error means exactly this; `GITHUB_REPOSITORY_NOT_ACCESSIBLE` means the repo URL is wrong or the Forte GitHub App isn't granted that repository. Pass `--repo` as `https://github.com/<owner>/<repo>`.
- **Forte projects contain three deployable resources**: services (containerized backends), websites (front-ends from GitHub, served on a CDN), and content. Services and websites are different primitives — see `references/setup-walkthrough.md` for which to recommend.
- **Services can be paused and resumed.** Pausing stops **all provisioned compute and its billing** for the service; while paused, requests to the service's endpoint return **503** with error code `SERVICE_PAUSED` and produce no request logs. Pause/Resume live on the console service page (also `pauseService` / `resumeService` on the server-side API) — there is **no** `forte services pause` CLI command; do not invent one. A paused service carries a `pausedAt` timestamp on its service object and a "Paused" badge in the console. **Deployments the customer triggers themselves** (console retry/deploy, config-change rebuilds) run normally and **automatically resume a paused service**; **GitHub-triggered builds (push or release) are skipped while the service is paused** — the build is recorded and immediately cancelled (free, with a "Build skipped" message), and the service stays paused. To deploy a skipped commit, resume the service and retry the build. Pausing is blocked while a build is in progress.
- **Forte detects deploy config from your real code — it does not assume language defaults.** At build time Forte inspects the actual repository to determine the listening port, the health-check path, the build/start commands, the package manager, the runtime version, and whether to use the repo's Dockerfile or generate one. **Never tell a customer "Forte defaults to port 3000 for Node" (or any per-language port) for deployment.** There is no such deploy-time default: the port and health-check path come from the real Dockerfile `EXPOSE` and the app's real HTTP routes, and if Forte can't determine them with confidence the **build fails with a specific, actionable error** rather than silently guessing. (The `3000`/`8000`/`8080` numbers exist only as a last-resort local forwarding target for `forte proxy` — unrelated to deployment.) Detected values are overridable and re-detectable (services: `--health-check-port`/`--health-check-path`/`--reset-healthcheck`/`--reset-dockerfile`; websites: `--build-command`/`--output-dir`/`--package-manager`/`--node-version`/`--reset-detected-config`). See `references/build-and-detection.md`.
- **Managed Databases are a project-level resource.** Forte offers two engines on the shared tier: **PostgreSQL** (open beta, self-serve) and a **MongoDB-compatible** document database (**closed alpha** — not self-serve; a customer must **request access from the engine tile** on the new-database page, and until it's granted the create API returns `MANAGED_DATABASE_TYPE_ACCESS_REQUIRED`). **Postgres is available to everyone now; the MongoDB engine is real and shipping but gated — say it's in closed alpha and how to request access, not that it's unavailable or "coming soon".** A database belongs to a *project* (not to a service or a signed-in user) and connects automatically to the services you attach it to: Forte creates a dedicated role, sets the env var names you choose (a connection URL in `DATABASE_URL` by default — a `postgresql://` string for Postgres, a `mongodb://` URI for MongoDB), redeploys the service, and **never reveals the generated password**. Storage is encrypted, connections require TLS, and Forte backs up every database **daily** — **do not promise point-in-time recovery, read replicas, high availability, an RPO, HIPAA readiness, or ephemeral branch-from-production databases; none of those exist.** Sizing is **storage-only** on the shared tier — customizable from **1 to 10 GB** (defaults to 2 GB), resizable within that range, so larger storage is **contact support** or the dedicated tier; the shared tier has no per-tenant compute sizing. Only the **shared** tier is self-serve — **dedicated is contact-support**. Customers manage databases from the **`forte databases` CLI command** (`list`/`get`/`create`/`update`/`delete`/`metrics`/`slow-queries`, plus `forte databases connections ...` to attach and detach services; `create` takes `--type postgres|mongodb`) or from the Databases tab of a project (`/console/projects/<projectId>/databases`). **There is still no SDK database API** — do not invent `forte.projects.databases.*` or similar. **When you connect a database to a service, first inspect the app's own code/config to learn how it reads its database** — the exact env var name(s) it expects (`DATABASE_URL`, `POSTGRES_*`/`PG*`, `MONGODB_URI`, or a framework-specific name), whether it wants a single connection URL or discrete host/port/user/password, and the connection-string dialect its driver needs (JDBC or R2DBC for Spring/Java, `prisma` for Prisma, `sqlalchemy` for SQLAlchemy) — then set the `forte databases connections add` `--*-var` and `--connection-string-format` flags to match, rather than accepting the `DATABASE_URL` default. A mismatch redeploys the service with variables it never reads and it still can't reach the database. See `references/databases.md` and `references/cli.md`.
- **Forte hosts DNS (beta) and sells domains — both live at the account level, under `/console/domains`, and both require a verified billing method.** **DNS hosting**: point a domain's nameservers at Forte (four vanity nameservers, `ns1`–`ns4.tryforte.dev`) and Forte becomes authoritative for it. A zone covers a **whole domain** (`example.com`) or a **subdomain** (`app.example.com`, leaving the rest on your current host); Forte hosts **one zone per domain tree**, so overlapping zones **merge** (the `--merge` flag / merge-on-create). Onboarding scans the domain's current DNS as a **starting point** (not a full copy) and can import a pasted BIND zone file — import missing records **before** switching nameservers, and **turn off DNSSEC** at the registrar first or the domain stops resolving. Connecting a website or service on a hosted domain **auto-writes the traffic + TLS-validation records**, which are marked **managed** and locked. Editable record types: `A`, `AAAA`, `CNAME`, `MX`, `TXT`, `NS`, `CAA`, `SRV`. Managed from the **`forte dns` CLI** or the console; **no SDK**. **Domain registration**: customers can **buy a domain directly in Forte** from `/console/domains` → **Register a domain** (console-managed — there is **no** `forte domains` CLI and no SDK; the only requirement is a verified billing method). The card is charged immediately and the domain, its DNS zone, and its nameservers are all set up in about a minute. **WHOIS privacy is always on**, **auto-renewal** is on by default, and transfer-out is available after the first 60 days; **DNSSEC is not available** on registered domains, and purchases aren't refundable. Registration runs through **Spaceship**, an ICANN-accredited partner registrar — customers get emails from Spaceship, including an **email verification they must complete within 15 days** or the domain is suspended. Forte is otherwise **not** a registrar for domains you already own — for those, bring the domain and either add a custom domain (CNAME) or move DNS hosting to Forte. See `references/dns.md`.
- **Three end-user auth methods are live**: Google OAuth, OTP (one-time passcode over email or SMS), and password sign-in — plus optional **multi-factor authentication** (a second factor: authenticator app/TOTP, passkeys/WebAuthn, email or SMS OTP, or backup codes), configured per project. Password and per-channel OTP login are toggled on in project settings; when MFA is enabled, login responses carry an `mfaStatus` and may return a short-lived pending token (usable only on the MFA endpoints until the second factor is verified). **Enabling email, phone, or password login — anything that makes Forte send email/SMS to end users — requires an APPROVED compliance registration on the account** (email also needs a verified SES domain, phone a `COMPLETE` SMS registration); the same gate that live payments sit behind. Google OAuth is exempt. See `references/auth-and-proxy.md`.
- **Sandbox (test) mode exists** as a project-level flag set **at creation time** — it is permanent and immutable (a project can't switch between live and sandbox). It unlocks hard-delete, contact-method overrides, **fixed test OTP codes** (a fixed 6-digit code assignable only to 555 test numbers or reserved test email domains like example.com/.test/.example/.invalid — accepted for verification, OTP login, and MFA challenges, with nothing actually delivered; see `references/auth-and-proxy.md`), default body logging, and Stripe test-mode payments. For *local* testing of a live service, use `forte proxy` (services only — websites are public-by-default and don't go through Forte auth). Multiple environments = multiple projects. See `references/api-surfaces.md`.
- **`forte.users.*` (browser, session cookie) and `forte.projects.*` (backend, `FORTE_API_TOKEN`) are two distinct API surfaces.** Never put `FORTE_API_TOKEN` in browser/client code. See `references/api-surfaces.md`.
- **Request logs and application logs are available from the CLI** (and the Forte dashboard). `forte requests` lists per-request invocation logs (status, latency, exception) and `forte requests get` shows one request in full; `forte logs` reads application log lines, filterable by request id, level, or full-text search. Both take `--json` for machine-readable output. To investigate "show me recent errors", follow `references/debugging.md`. Only **services** produce these — websites bypass the gateway, so they have no request logs or metrics.
- **Services get no CPU between requests, so background work runs through Actions.** Memory stays provisioned (no cold starts), but CPU is scaled to zero whenever no request is in flight. **Never add, or carry over, an in-process scheduler or post-response background work**: `@Scheduled`, `ScheduledExecutorService`, `setInterval`, node-cron, APScheduler, Celery beat, a Procfile `worker:`, fire-and-forget promises or threads. It won't fire reliably. Convert it to a Forte Action instead. For long-running, persistent, or stateful workers (queue consumers, always-on bots, work that can't be split into pieces under 120s), don't invent a workaround. Say that Forte is building longer-running background workers, and point the customer to support@forteplatforms.com for early access. See `references/actions.md` and the "Background work and schedulers" section of `references/setup-walkthrough.md`.
- **Forte Actions (beta) call one of your Forte services on a schedule.** `forte actions ...` registers a target **service + path** (like a payment trigger) that Forte sends a POST to — either on a recurring cron schedule (with a timezone) or once at a specific time (also creatable from code, e.g. a follow-up scheduled at sign-up). The target service must belong to the same project, and it autoscales to handle invocations. **The handler does the work inside the request and returns `2xx` when done**, within **120 seconds**. Never "ack fast and enqueue". Split larger jobs with a recurring sweeper, or by self-chaining (process a chunk, save a cursor, `createActionInvocation` for the next one). Each execution is recorded as an *invocation*; actions can be marked retryable, paused/resumed, invoked on demand, and have pending invocations cancelled. Minimum cadence is once per minute. See `references/actions.md`.
- **Service env vars `FORTE_PROJECT_ID`, `FORTE_SERVICE_ID`, `FORTE_API_TOKEN` are injected automatically** inside Forte-hosted services. Websites do NOT receive these — websites are public front-ends and don't authenticate against Forte. Do not use the `FORTE_` prefix for custom env vars — it is reserved. On **websites** the `AWS_` prefix is also reserved (they run on AWS Lambda), but **services** allow `AWS_*` variables.
- **Website traffic never passes through the Forte gateway — this includes server-rendered (SSR) websites.** Services are gateway-proxied: Forte authenticates every request (injecting the `X-Forte-User-Id` header), enforces auth path exclusions, and captures per-request logs and metrics. Websites — static *and* SSR — are served directly from the CDN, so **none** of that applies: no Forte auth enforcement, no `X-Forte-User-Id`, no request logs, no metrics. An SSR website's server code runs, but Forte never sees or authenticates the individual request, so the site must enforce its own auth. For authenticated, observable request handling, deploy a **service** and call it from the website. The **one** website-level gate Forte does offer is **site password protection** — a single shared password enforced at the CDN edge, set via `forte websites update <projectId> <websiteId> --site-password <pw>` (remove with `--remove-site-password`), **SSR websites only**. It is a static site-wide password challenge, **not** Forte end-user authentication (no users, sessions, or `X-Forte-User-Id`). See `references/setup-walkthrough.md`.
- **Same-site session cookies on services use the reserved `/_forte` path.** For browser-direct `forte.users.*` calls from a service's own frontend, point the SDK at the service's origin via `new ForteClient({ baseUrl: '/_forte' })` so the `Forte-User-Session-Token` cookie stays first-party. Services only — websites bypass the gateway, so `/_forte` doesn't exist there. See `references/auth-and-proxy.md`.

## Quick Command Reference

```
forte login                                                           # authenticate (opens browser)
forte whoami                                                          # verify auth
forte projects list                                                   # list all projects
forte projects create <name>                                          # create a project
forte services list <projectId>                                       # list services (shows repo · branch)
forte services create <projectId> --name <n> --repo <url> --branch <b>
forte requests <projectId> <serviceId>                               # recent failing requests (5xx by default)
forte requests <projectId> <serviceId> --status 400 403 --since 24h  # specific status codes
forte requests get <projectId> <serviceId> <requestId>              # full request detail (exception, bodies)
forte logs <projectId> <serviceId> --request <requestId> --level ERROR   # logs one request produced
forte logs search <projectId> <serviceId> --search "<text>"        # full-text log search
forte websites list <projectId>                                       # list websites
forte websites create <projectId> --name <n> --repo <url> --branch <b>
forte websites deploy <projectId> <websiteId> [--commit <sha>]       # trigger/rollback deploy
forte databases list <projectId>                                     # list managed databases
forte databases create <projectId> --name <n> [--type postgres|mongodb] [--storage <gb>]
forte dns list                                                        # list hosted DNS zones (beta)
forte dns create <domain> [--merge]                                   # host a domain's DNS on Forte
forte dns sync <dnsZoneId>                                            # re-check nameserver delegation
forte dns records add <dnsZoneId> --name <n> --type <A|CNAME|...> --value <v> [--ttl <s>]
forte actions list <projectId>                                       # list actions (beta)
forte actions create <projectId> --name <n> --service <serviceId> --path </p> --schedule recurring --cron "0 9 * * *" --timezone <tz>
forte actions create <projectId> --name <n> --service <serviceId> --path </p> --schedule one-time --at <iso8601>
forte actions invoke <projectId> <actionId>                          # run once on demand
forte actions invocations <projectId> <actionId>                     # list past invocations
forte payments list <projectId> <userId>                             # list a user's payments (beta)
forte payment-methods list <projectId> <userId>                      # list a user's saved payment methods — cards & bank accounts (beta)
forte payment-triggers list <projectId>                              # list payment-event webhooks (beta)
forte proxy [--project-id <id>] [--service-id <id>] [-p <port>]     # local dev proxy (services only)
```

Omitting a required `projectId` / `serviceId` / `websiteId` / `userId` drops into an interactive picker. `references/cli.md` is the complete, exact command + flag surface — consult it before using any flag.
